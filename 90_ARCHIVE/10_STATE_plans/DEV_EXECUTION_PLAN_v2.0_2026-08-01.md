## 0. 실행 결론

가장 빠른 알파는 기능을 절반만 만드는 버전이 아니다. **무료 실제 VPN + 순간 중심 UX + 3잔액 데이터 지갑 + 실제 보호 확인 + 양쪽 추천 보상**까지 하나의 완결된 무료 알파로 만든다. 실제 카드 결제는 PG·사업자·환불·법무 경계 때문에 무료 알파와 분리해 A1 유료 알파로 후행한다.

- 첫 가시 변화 목표(TTFV): 구현 시작 후 **4~6 개발시간** 안에 R3 `진실한 상태 UI` 공개
- A0 무료 알파 후보: **44~60 개발시간**
- A0 외부 알파 목표: 서버 접근이 준비된 뒤 **최단 5개 작업일**
- A1 유료 알파: PG·사업자·정책 승인 후 별도 일정
- 일정 숫자는 추정이다. 실제 서버·기기·외부 승인 대기시간은 포함하지 않으며 매 릴리스에서 실측으로 갱신한다.

속도를 위해 생략하지 않는 것은 실제 보호 상태, 킬 스위치, DNS/IPv6 누수 방지, 재연결, 잔액 무결성, 추천 중복 지급 방지, 공개 검증이다.

## 1. 알파의 정확한 범위

### 1.1 A0 무료 알파에 반드시 포함

1. 월 1GB 무료 실제 쿼터
2. 무료·추천·구매 3잔액 지갑과 차감 순서
3. 공용 Wi-Fi·여행·지역 웹·연결 문제의 순간 카드 4개
4. 목적 선택 없이 시작하는 바로 연결 경로
5. 공식 WireGuard 앱 설정과 사용자 기기 내 개인키 생성
6. 실제 터널·출구 IP·최근 확인 시각을 사용한 보호 상태
7. DNS·IPv6 보호와 OS별 킬 스위치 안내·검증
8. Wi-Fi↔모바일·절전·재시작 후 재연결 검증
9. 실제 가동 서버만 보여 주는 카탈로그
10. 세션 사용량·잔액 변화·최대 2분 동기화 지연 고지
11. 친구의 첫 실제 터널 + 누적 100MB 후 양쪽 500MB
12. 추천인 월 5건 상한과 자기·순환·중복 추천 차단
13. 활성 기기 키 2개와 즉시 폐기
14. 개인정보·로그·삭제·장애 상태의 정직한 화면

### 1.2 A0에서 실제로 작동하지만 돈은 받지 않는 부분

- 3GB·10GB·30GB 충전 UI와 최종 확인 화면
- 운영자 전용 서명 테스트 크레딧으로 구매 잔액 원장·차단 해제 왕복 검증
- 가격은 `지불의사 미검증`, 결제는 `알파에서 비활성`으로 명확히 표시

테스트 크레딧은 실제 결제나 유료 사용자 증거가 아니다.

### 1.3 A1 유료 알파로 분리

- 실제 PG 승인·취소·영수증·환불·분쟁
- 통신판매·세금·사업자 계약
- 실제 카드·계좌 결제
- 환불 후 잔액 회수·이미 사용된 잔액 처리

외부 결제 대기가 A0 무료 VPN 공개를 막지 않도록 릴리스를 분리한다.

### 1.4 알파에서 제외

- 네이티브 자체 VPN 클라이언트
- 20개국 동시 확장
- 100GB·300GB 기본 판매
- 스트리밍 해제 보장
- P2P·고강도 검열 우회
- 출석·레벨·배지·광고
- 자동 연락처 업로드

## 2. 알파 사용자 경험

### 2.1 첫 사용 흐름

1. **시작** — “VPN이 가끔 필요하다면 매달 내지 마세요.”
2. **약속 확인** — 월 1GB 무료, 추천·구매 데이터 무기한, 자동결제 없음
3. **최소 동의** — 수집 정보, 개인키 경계, 삭제 방법
4. **기기 설정** — 브라우저에서 WireGuard 키를 만들고 공개키만 서버로 전송
5. **순간 선택** — 공용 Wi-Fi·여행·지역 웹·연결 문제 또는 바로 연결
6. **WireGuard 이동** — 공식 앱에서 프로필 가져오기
7. **보호 확인** — PWA로 돌아와 실제 출구 IP·최근 핸드셰이크 확인
8. **세션 종료** — 사용량, 남은 잔액, 다음에 쓸 수 있는 예상치

### 2.2 반복 사용 흐름

1. 홈에서 마지막 정상 서버와 현재 잔액 확인
2. 바로 연결 또는 순간 카드 선택
3. 공식 WireGuard 앱에서 터널 시작
4. PWA의 `보호 확인`으로 실제 상태 확인
5. 종료 뒤 세션 요약 확인

PWA는 OS VPN을 직접 켰다고 가장하지 않는다. 버튼 이름도 `VPN 연결`보다 `WireGuard에서 연결`과 `보호 확인`을 사용한다.

### 2.3 추천 흐름

1. 첫 성공 세션 또는 두 번째 성공 세션 뒤 추천 제안
2. 링크·QR·메신저 공유
3. 친구가 추천 토큰으로 가입
4. 첫 실제 터널 성공
5. 누적 100MB 달성
6. 하나의 데이터베이스 트랜잭션으로 양쪽 500MB 지급
7. 양쪽 데이터 지갑과 추천 진행 화면에 반영

### 2.4 잔액 부족 흐름

1. 50%, 20%, 100MB에서 조용한 알림
2. 현재 세션 사용 속도로 부족 가능성 표시
3. A0에서는 무료·추천 데이터 획득 안내와 테스트 크레딧만 제공
4. A1에서는 3GB·10GB 중심 결제로 연결
5. 월 50GB 초과 예상 시 정액제가 유리할 수 있음을 먼저 표시

## 4. 기술 아키텍처

### 4.1 구성

| 계층 | 알파 채택 | 책임 |
|---|---|---|
| 공개 앱 | GitHub Pages PWA v2 | 화면·클라이언트 키 생성·API 호출·정직한 상태 |
| 제어 API | Python 최소 API 서비스 | 세션·서버 카탈로그·지갑·추천·기기 계약 |
| 제어 저장소 | SQLite WAL + append-only 원장 | 알파 100명 계정·잔액·추천·멱등 사건 |
| 패널 노드 | Hetzner 계열 별도 노드 | API·DB·봇·모니터링·백업 |
| exit 노드 | 서로 다른 공급자 최소 2곳 | WireGuard 터널·사용량 카운터·차단 |
| 알림 | Telegram bot | 동의·claim·상태·폐기·장애 알림 |
| 공개 확인 | `/v1/check` | 요청이 실제 exit IP를 통과했는지 무상태 판정 |

SQLite는 A0의 단일 제어 노드·100명 범위에서 가장 빠른 선택이다. WAL, 트랜잭션, 원자 백업을 사용하고 쓰기 경합·복구시간이 기준을 넘으면 PostgreSQL로 이동한다. PostgreSQL을 미리 도입해 알파를 늦추지 않는다.

### 4.2 데이터 모델

| 엔터티 | 핵심 필드 | 무결성 규칙 |
|---|---|---|
| accounts | account_id, consent_version, created_at | HMAC 가명 ID, 원 Telegram ID 저장 금지 |
| sessions | token_hash, account_id, expires_at, revoked_at | 원 토큰 저장 금지, 만료·회전 |
| devices | device_id, account_id, wg_public_key, status | 계정당 활성 2개, 공개키 유일 |
| wallet_entries | entry_id, account_id, bucket, delta, reason, idem_key | append-only, idem_key 유일, 합계 음수 금지 |
| usage_events | node_id, peer_id, epoch, rx, tx, idem_key | 누적 카운터 롤백 처리, 중복 수신 무효 |
| referrals | referral_id, inviter, invitee, token_hash, status | 자기·순환·중복 귀속 금지 |
| reward_events | referral_id, side, bytes, idem_key | 양쪽 지급을 한 트랜잭션으로 처리 |

| audit_events | category, subject, result, timestamp | 방문 사이트·콘텐츠·DNS 원문 금지 |

### 4.3 지갑 처리

1. 사용량 사건을 멱등 키로 수신한다.
2. 누적 카운터에서 검증된 증가분만 계산한다.
3. 무료→추천→구매 순서로 한 트랜잭션에서 차감한다.
4. 차감 뒤 사용 가능 잔액이 0이면 차단 스냅샷을 만든다.
5. 스냅샷을 exit 노드에 서명 전달한다.
6. exit 노드가 적용 결과를 회신하면 상태를 확정한다.
7. 저장 실패 시 기존 차단 상태를 임의로 풀지 않고 오류를 표시한다.

### 4.4 추천 처리

1. 256비트 무작위 추천 토큰 생성 후 해시만 저장한다.
2. 신규 계정에 한 번 귀속한다.
3. 첫 보호 성공 사건과 누적 100MB를 확인한다.
4. 추천인 월 5건 상한과 자기·순환·중복·속도 제한을 확인한다.
5. 하나의 트랜잭션에서 추천인·피추천인 `earned` 항목을 각각 +500MB 기록한다.
6. 동일 referral_id 재실행은 기존 결과를 반환하고 재지급하지 않는다.
7. 의심 건은 지급 전 보류하며 이미 사용한 보상을 음수로 회수하지 않는다.

### 4.5 인증과 토큰

- 기존 Telegram HMAC 가명 ID와 10분 1회용 claim을 유지한다.
- claim 교환 뒤 짧은 access token과 회전 가능한 device session을 발급한다.
- 토큰 원문은 로그·URL·Git에 남기지 않는다.
- PWA 저장은 IndexedDB를 우선 사용하고 실패하면 메모리 세션으로 계속 작동하되 재방문 유지 불가를 알린다.
- 서드파티 스크립트를 쓰지 않고 엄격한 CSP로 XSS 표면을 줄인다.

### 4.6 WireGuard 개인키

알파의 기본 경로는 브라우저의 검토된 X25519 구현으로 개인키를 기기 안에서 생성하고 공개키만 API에 전송하는 것이다.

- 2시간 기술 스파이크에서 iOS Safari·Android Chrome·Windows Chrome 지원을 확인한다.
- 생성 직후 네트워크·로그·오류 보고에 개인키가 0회 등장하는지 검사한다.
- 지원 실패 시 공식 WireGuard 앱에서 키를 생성하고 공개키만 붙여넣는 수동 경로로 전환한다.
- 서버에서 개인키를 생성해 편의를 얻는 우회는 사용하지 않는다.

### 4.7 실제 보호 확인

`/v1/check`는 요청 출발 IP가 가동 중인 FreeFlexVPN exit IP인지, 서버 상태가 정상인지, 확인 시각이 언제인지 반환한다. PWA는 다음 세 근거를 조합한다.

1. 공개 확인 엔드포인트가 exit IP를 확인
2. 해당 피어의 최근 WireGuard 핸드셰이크가 허용 시간 안에 존재
3. DNS·IPv6·킬 스위치 검증 상태가 목표 OS 계약을 충족

브라우저가 확인할 수 없는 항목은 `확인 불가`로 표시하며 보호됨으로 승격하지 않는다.

### 10.2 필수 음성 대조

- 서울 서버를 카탈로그에 넣으면 실패
- PWA 버튼만 ON이고 check가 직접 IP이면 보호됨 검사가 실패
- DNS 또는 IPv6 확인 실패를 보호됨으로 승격하면 실패
- 같은 usage event를 두 번 보내도 한 번만 차감
- 저장을 강제 실패시켜도 원장 원본과 기존 차단 상태 보존
- 추천인=피추천인이면 실패
- A→B→A 순환 추천이면 지급 보류
- 자격 사건을 동시에 두 번 보내도 양쪽 각 500MB 한 번만 지급
- 월 6번째 추천은 지급하지 않고 명시 상태 반환
- 개인키가 네트워크 요청·로그·DOM 영구 저장에 나타나면 실패
- 100GB·300GB가 기본 가격 화면에 나타나면 실패

3. 공개 진입점 무캐시 HTTP 최소 3회

## 17. 실행 시작 체크리스트

## 19. 다음 행동

실행의 첫 칸은 **R3-ui-truth**다. 대한민국·서울 허구 항목을 제거하고, 실제 가동 서버만 표시할 수 있는 카탈로그 계약과 보호 상태 5단계를 v2 화면에 적용한다. 이 릴리스는 실제 서버가 없어도 공개 가능하며, 새 기획을 사용자가 가장 빨리 화면에서 확인하는 변화다.
